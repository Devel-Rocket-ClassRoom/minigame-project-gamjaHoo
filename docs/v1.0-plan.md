## 1. V0.1 → V1.0 비전

### V0.1 (마무리 — 2026-05-22)
- "한 시즌이 끝까지 진행되는 최소 게임 루프 검증" — 달성.
- 결과 우선 모델 + 단순화 + 단일 포메이션 + 텍스트 시뮬 없음.

### V1.0 목표
- **"한 시즌이 *재미있게* 진행"** (`project-context.md`).
- 사용자 의사결정 깊이 ↑ — 시설·전술·이적·유스 4축이 의미 있는 트레이드오프를 갖도록.
- 정보 비대칭 본격 도입 (스카우트 시스템 / 트레잇 노출 정도) — `design-decisions.md` #14 정신 강화.
- 사기 / 약속 / 면담 시스템 — 선수 한 명이 단순 능력치 객체가 아니라 의사결정 상대로.
- 매치 텍스트 이벤트 — 동수칸/종식이 콘텐츠처럼 *읽는 재미*.

### 비전 vs V0.1 차이 한 줄
- V0.1: "스코어가 나온다."
- V1.0: "왜 졌는지 텍스트로 읽고, 다음 매치에 누구를 선발할지 고민하고, 사기 떨어진 에이스 면담하고, 시즌 종료 후 보드에 예산 요청한다."

## 3. 범주별 명세

### 3.1 선수 능력치 (Stats)

**V0.1 동작:**
- 카테고리: Technical(12) / Mental(12) / Physical(8) / Goalkeeping(10) = 42개 필드.
- 스케일 1-20 (FM 표준).
- CA-Stats 분리 운영 (`design-decisions.md` #24) — 매치는 CA 만 사용, stats 는 표시용.
- UI 노출 — `PlayerProfileController` 가 `isDebugMode` 일 때만 정확 수치 표시, 평시는 5단계 티어.

**V1.0 변경:**

#### 3.1.1 스케일 1-100 전환 (사용자 피드백 2.3, Q12 확정)
- **결정:** Stats 1-100 (FM 표준 1-20 → 5배 세분화) + **CA / PA 1-200 (FM 표준 그대로)**.
- 모든 stats 필드 `int` 1-100. 새 스케일 → 외부화 수치 전부 재산정 필수.
- 매핑 가이드 (재밸런싱 기준 — FM 1-20 ↔ V1.0 1-100):
  - FM 1-3 (terrible) ≈ 1-15 (V1.0)
  - FM 4-7 (poor) ≈ 16-35
  - FM 8-12 (average) ≈ 36-60
  - FM 13-16 (good) ≈ 61-80
  - FM 17-20 (elite) ≈ 81-100
- `ClampStat` / `statMeanAtCAFloor` / `statMeanAtCACeil` 등 외부화 수치 전부 1-100 기준 재산정.
- **CA / PA 는 FM 표준 1-200 그대로**. UI 표시 시 단위 차이 명확 ("CA 145" vs "Passing 72") — 도메인 관례 일관.
- **영향 범위:** `Stats.cs` 4 카테고리 / `PlayerGenerator` 3단계 / `GameBalanceSO` ~25 필드 / 시드 자산 / UI 표시.

#### 3.1.2 카테고리 재정의 (사용자 피드백 2.3, Q1 확정 — **실제 FM26 1:1 매핑**)
- **확정:** 실제 FM26 카테고리 1:1 매핑. 총 49개 stats (Tech 14 / Mental 14 / Phys 8 / GK 13).
- **Technical 14**: Corners, Crossing, Dribbling, Finishing, First Touch, Free Kick Taking, Heading, Long Shots, Long Throws, Marking, Passing, Penalty Taking, Tackling, Technique
- **Mental 14**: Aggression, Anticipation, Bravery, Composure, Concentration, Decisions, Determination, Flair, Leadership, Off the Ball, Positioning, Teamwork, Vision, Work Rate
- **Physical 8**: Acceleration, Agility, Balance, Jumping Reach, Natural Fitness, Pace, Stamina, Strength
- **Goalkeeping 13**: Aerial Reach, Command of Area, Communication, Eccentricity, First Touch (GK), Handling, Kicking, One on Ones, Passing (GK), Punching Tendency, Reflexes, Rushing Out (Tendency), Throwing
- **V0.1 → V1.0 매핑 (Save Migration 무효 — Q8, 단 명세상 추적)**:
  - V0.1 12 Tech → 14 Tech (Marking / Technique 신규 추가)
  - V0.1 12 Mental → 14 Mental (Anticipation / Bravery / Flair 보강, off the ball 명칭 정정)
  - V0.1 8 Physical → 8 Physical (Jumping → Jumping Reach 명칭만)
  - V0.1 10 GK → 13 GK (First Touch / Passing / Punching Tendency 신규)
- **매치 엔진 영향 (§3.5)**: 라인별 가중 평균 사용 → stats 수 자체는 무관. 단 특정 이벤트는 해당 stat 직접 참조:
  - Shot 결과 분기 → `finishing × composure / 100`
  - Save → GK `reflexes × handling / 100`
  - Foul → `aggression`
  - 골 결정자 가중 → `finishing × offTheBall`
  - Cross → `crossing × technique`
  - 등 (§3.5.3 이벤트 표 참조).

#### 3.1.3 Absolute vs Relative 분리 (FM 표준, 신규 도입)
- **Absolute** (훈련으로 거의 안 자람, 인성 기반): Determination, Work Rate, Leadership, Flair, Bravery, Aggression, Concentration, Natural Fitness, Composure, Decisions.
- **Relative** (훈련으로 성장 가능): 나머지.
- V1.0 성장 시스템 (§3.9 mentoring / training) 에서 Absolute 변화율 ↓.
- 데이터 구조: `Stats.cs` 에 메타 X (Absolute 여부는 stat name 기준 하드코딩 또는 별도 `StatMetadata.cs` SO).

#### 3.1.4 Hidden Attributes (V1.0 신규 — 사용자 피드백 2.6 / FM 표준)
- 별도 도메인 객체 `Player.hiddenAttrs: HiddenAttributes` (1-100):
  - `loyalty` (충성도) — 재계약 시 주급 요구 ↓, 이적 요청 ↓
  - `ambition` (야망) — 상승 욕구. 빅클럽 오퍼 / 출전시간 부족 시 이적 요청 ↑
  - `professionalism` (프로페셔널) — 훈련 효율 / 사기 안정
  - `pressureHandling` (압박 내성) — 빅매치 평점 보정
  - `temperament` (기질) — 카드 / 라커룸 분위기
  - `controversy` (논란성) — 미디어 사고 확률 (V1.x 미디어 시스템 도입 시)
  - `injuryProneness` (부상 빈도) — 부상 발생률 보정
  - `consistency` (일관성) — 폼 변동폭
  - `versatility` (다재다능) — 2차 포지션 적응 속도
- **노출 정책 (§3.7 스카우트 연동)**: 스카우트 명단에 들어간 선수만 일부 노출. 스카우트 시설 등급 ↑ → 노출 정도 ↑.
- **트레잇 수치형 흡수**: 사용자 피드백 2.4 "trait 의리·부상빈도 0-20" → **이미 Hidden Attributes 가 해당**. Trait 은 별개 카테고리 (§3.2 참조).

#### 3.1.5 노출 정책 변경 (사용자 피드백 2.3)
- `isDebugMode` 와 무관하게 **항상 stats 정확 수치 노출** (자기 구단 선수 한정).
- 타 구단 선수: 스카우트 명단에 들어간 선수만. 미들어간 선수 = 범위만 표시 ("패스 60-75").
- CA / PA 도 자기 구단 한정 정확 수치, 타 구단은 스카우트 결과만. `isDebugMode` 는 **모든 선수 정확 수치 노출** 용도로 의미 보존.

### 3.2 선수 특성 (Trait)

**V0.1 동작:**
- TraitSO: `id / displayName / description / weight / exclusionGroupId`.
- 6개 트레잇 (늦깎이형 / 조숙형 / 부상취약 / 멘탈강자 / 빅매치형 / 만능형).
- **Player.traitIds: List<int>** (있/없 binary).
- 효과 없음 (라벨만, `algorithms.md` #1 V1.0 Notes).

**V1.0 변경:**

#### 3.2.1 Trait 재정의 — **카테고리화**
사용자 피드백 2.4 "수치형" 은 §3.1.4 Hidden Attributes 로 흡수. Trait 은 본래 의미인 **명시적 플레이스타일 마커** 로 재정의:

| 카테고리 | 예시 | 효과 |
| --- | --- | --- |
| **플레이스타일** | 빅매치형 / 늦깎이형 / 클러치 / 무리한 패스 / 와이드 플레이 | 매치 시뮬 분기 (5단계 득점자 추첨 가중 / 폼 보정 등) |
| **부상/체력** | 유리몸 (`injuryProneness` 의 명시적 큰 효과) | injuryProneness 보정 + 부상 시스템 분기 |
| **성장곡선** | 조숙형 / 늦깎이형 / 슈퍼유망주 | 성장률 가중 |
| **포지션 특화** | 멀티포지션 / 골 결정력 / 수비형 윙백 | 포지션 적응 / 매치 행동 분기 |

#### 3.2.2 효과 본격 도입
- TraitSO 에 `effects: List<TraitEffect>` 필드 추가.
- `TraitEffect` 종류 (enum):
  - `MatchModifier` — 매치 시뮬 시 특정 이벤트 확률 곱셈 (예: 빅매치형 = 빅매치 평점 ×1.15)
  - `GrowthRateModifier` — 훈련 시 특정 stat 성장률 보정 (예: 조숙형 = 18세까지 ×1.5, 23세 이후 ×0.5)
  - `InjuryRateModifier` — 부상 발생률 곱셈
  - `MoralePropensity` — 사기 변동 폭 보정 (예: 멘탈강자 = 사기 하락 ×0.5)
  - `MarketValueModifier` — 시장가 가중 (`algorithms.md #3` 트레잇 가치 V1.0 Notes)
- **충돌 그룹 확장**: `exclusionGroupId` 추가 정의 — 성장곡선 그룹 (조숙/늦깎이/표준), 부상 그룹 (유리몸/철인), 등.

#### 3.2.3 노출 정책
- 스카우트 명단에 들어간 선수만 일부 트레잇 노출.
- 시설 등급 ↑ → 노출 트레잇 수 ↑.
- 자기 구단 선수 = 모두 노출.

- AI 응답 (선수 측):
  - 주급 ↑ ≥ 현재 ×1.20 → 거의 무조건 수락
  - 주급 ↑ ≥ 현재 ×1.05 → 평가 (`loyalty` + `ambition` + 현재 사기 기반)
  - 주급 동일 / 하락 → loyalty 높을수록 수락 가능성 ↑
- 재계약 시 **사기 회복** — `state.morale = Min(100, state.morale + balance.contractRenewalMoraleBoost)`.

#### 3.3.2 계약 옵션 확장
- `Contract.cs` 에 신규 필드:
  - `signingBonus: int` — 사이닝 보너스 (V1.0 신규 — `algorithms.md #3` Market Value V1.0 노트 일부)
  - `loyaltyBonus: int` — 충성 보너스 (재계약 시 사용)
  - `appearanceBonus: int` — 출전 보너스 (시즌당)
  - `goalBonus: int` — 골 보너스 (시즌당)
  - `releaseClause: int` (기존, 활성화) — 외부 클럽이 release clause 이상 오퍼 시 협상 강제
- 위 모두 옵션 (기본 0). UI 협상 화면에서 입력.

#### 3.3.3 자유계약 (FA) 흐름
- `SeasonEndProcessor.Run` 의 FA 전환 (V0.1) 유지.
- **잔여 6개월 시점** 부터 자유계약 협상 가능 — `RenewContract` 또는 **타 구단이 미리 계약** (보스만 룰).
- V1.0 도입: `TransferSystem.SubmitFreeAgentContract(player, newClub, contract)` — 만료 6개월 이내 선수에게 타 구단이 직접 계약 제안. 이적료 0, 사이닝 보너스만 발생.

### 3.4 선수 사기 / 기분 (Morale System)

**V0.1 동작:**
- `PlayerState.morale: int` — 0~100, 시즌 시작 50 리셋, **변동 없음** (사기 시스템 미구현).
- `PlayerState.form: int` — 위와 동일.

**V1.0 변경 — 사기 시스템 본격 도입:**

#### 3.4.1 Morale + Happiness 분리
- `Morale` (사기, 0-100) — **단기 변동**. 최근 매치 / 라커룸 분위기 / 코칭 코멘트 기반.
- `Happiness` (행복도, 0-100) — **장기 추세**. 약속 이행 / 출전시간 / 구단 성적 / 재계약 기반.
- Player.state 에 `happiness: int` 신규.

#### 3.4.2 변동 트리거 (V1.0 도입)
| 트리거 | Morale 변동 | Happiness 변동 |
| --- | --- | --- |
| 매치 승리 | +5 ~ +10 (역할별) | - |
| 매치 패배 | -5 ~ -10 | - |
| 빅매치 승리 | +15 | +3 |
| 강등 | -30 | -50 |
| 우승 | +30 | +20 |
| 자기 평점 7.5+ | +5 | - |
| 약속 출전시간 미달 (시즌 30% 미만) | - | -20 / 월 |
| 약속 영입 미이행 | - | -15 |
| 보드 약속 미이행 | - | -25 |
| 재계약 (주급 ↑) | +15 | +25 |
| 면담 (긍정) | +5 | +5 |
| 면담 (부정) | -5 | -10 |
| 라커룸 (긍정 캡틴) | +2 / 주 | - |

#### 3.4.3 Happiness 임계점 → 행동 분기
- Happiness ≥ 80: **만족** — 추가 사기 보너스 / 폼 ↑
- 60 ~ 79: **양호** — 정상
- 40 ~ 59: **불만 표시** — 인터뷰 사고 가능성 ↑
- 20 ~ 39: **이적 요청** — `TransferRequestEvent` 발행. AI 처리: 자동 transferListed 또는 유저 응답 대기
- < 20: **반항** — 훈련 거부 / 매치 평점 하락

#### 3.4.4 Hidden Attribute 연동
- `loyalty` 높을수록 Happiness 하락폭 ↓.
- `ambition` 높을수록 출전시간 미달 / 강등 시 Happiness 하락폭 ↑.
- `professionalism` 높을수록 변동폭 전체 ×0.7.

#### 3.4.5 Promise 시스템 (V1.0 신규 — FM 표준)
- **약속 종류**:
  - 출전시간 보장 (Star Player / Important / Squad / Backup / Hot Prospect / Future / Junior — FM 7단계, V1.0 5단계로 축약)
  - 영입 약속 (시즌 시작 시 특정 포지션 영입)
  - 새 계약 약속 (다음 시즌 시작 시 재계약)
  - 이적 약속 (다음 활성화 기간에 이적 허용)
- 데이터 구조: `Player.promises: List<Promise>` 또는 `GameState.activePromises: List<Promise>`.
- `Promise.cs`:
  ```csharp
  public class Promise {
      public int id;
      public int playerId;
      public PromiseType type;        // PlaytimeAgreement / TransferIn / Renewal / TransferOut
      public DateTime madeAt;
      public DateTime deadline;
      public PromiseStatus status;    // Active / Fulfilled / Broken
      public Dictionary<string, int> targets;  // type 별 가변 (예: "minLeagueAppearances": 20)
  }
  ```
- 매일 `DailyProcessor` 가 `PromiseSystem.CheckProgress(state)` 호출 → 마감 임박 / 미이행 시 Happiness 변동.

#### 3.4.6 면담 시스템 (V1.0 — 단순 도입)
- 유저가 선수 프로필에서 [면담] → 4 ~ 6 가지 사전 정의된 멘트 선택지:
  - "출전시간 보장하겠다" (PlaytimeAgreement Promise 생성)
  - "다음 시즌 새 계약 협상하자" (Renewal Promise)
  - "현재 성과를 칭찬한다" (즉시 Morale +5)
  - "더 노력해야 한다" (즉시 Morale -3, 단 professionalism 높은 선수는 -1)
- 각 선택지의 효과는 `loyalty` / `ambition` / `professionalism` 에 따라 다름.

#### 3.4.7 라커룸 분위기 (V1.0 단순 도입)
- `Club.season.dressingRoomMood: int` (0-100) — 모든 1군 선수의 Happiness 평균.
- 캡틴 / 부캡틴 leadership 가산점.
- 라커룸 분위기 < 30 → 시즌 폼 전체 -5 보정 (매치 결과에 영향).

### 3.5 매치 시뮬레이션 (Match Engine)

**V0.1 동작:**
- 단일 `Simulate(match, state, balance) → MatchResult`.
- 결과 우선 모델: 시드 → starting11 (top-11 by CA) → Poisson 골수 → 라인 가중 득점자.
- `strengthExponent k=1.5` 임시 변통.
- PlayerMatchStat: goals + minutesPlayed=90 만. assists / rating / cards = 0.

**V1.0 변경 — 분 단위 이벤트 시퀀스 (`design-decisions.md` #34):**

#### 3.5.1 인터페이스 보존
- `MatchSimulator.Simulate(match, state) → MatchResult` 시그니처 유지 (호출자 `GameLoop` / `BackgroundSimulator` / `MatchPostProcessor` 영향 없음).
- 내부만 전면 재작성.

#### 3.5.2 분 단위 이벤트 엔진
```
1. 시드 고정 (V0.1 동일)
2. starting11 결정 — V1.0 라인업 시스템 (§3.6) 산출물 사용
3. 경기 상태 초기화 (minute=0, score=0:0, 11명 출전, 카드/부상 0)
4. 매 분 step (1~90, 컵은 ~120 + 승부차기):
   a. 이벤트 종류 추첨 (Shot / Pass / Tackle / Foul / Card / Injury / Sub / no-event)
   b. 이벤트 주체 선수 추첨 (포지션 + 스탯 + 폼 + 사기 기반)
   c. 이벤트 결과 분기 (Shot → Goal / Save / Miss / Block, Foul → Yellow / Red / nothing 등)
   d. 누적 상태 갱신 (score, cards, injuries, substitutions)
   e. AI 교체 판단 (SubstitutionAI — 피로/부상/스코어 상황)
5. 최종 누적 = MatchResult
```

#### 3.5.3 이벤트 종류 정의
| 이벤트 | 발생 조건 / 확률 공식 | 결과 분기 |
| --- | --- | --- |
| Shot | 공격팀 strength 비례, AT 라인 ↑ | Goal / Save / Miss / Block (`finishing` × `composure` 가중) |
| Save | Shot 결과의 한 분기 | GK `reflexes` × `handling` |
| Foul | 양 팀 `aggression` 합 기반 | Yellow / Red / 그냥 휘슬 (Yellow 2장 = Red) |
| Injury | starting11 × `injuryProneness` × 매치 강도 | InjuryInfo 생성 + 교체 트리거 |
| Pass | 양 팀 패스 가중 | 점유율 통계용 |
| Cross | LW/RW 출전 + crossing 스탯 | Goal 시도 → Shot 분기 |
| OffsidesCalled | ST 라인 offside 트레잇 / 평균 |  |
| Substitution | AI 판단 (피로 70+ / 부상 / 스코어) | 벤치에서 11명으로 교체 |

#### 3.5.4 PlayerMatchStat 확장
- `goals` — 4단계 라인 가중 (V0.1) → 분 단위 자연 발생
- `assists` — 골 직전 패스 선수 (Shot 이벤트 시 어시스트 추첨)
- `minutesPlayed` — 교체 / 퇴장 반영 (가변)
- `rating` — V1.0 평점 시스템 (별도 §3.5.7)
- `yellowCards / redCards` — Foul 이벤트 누적
- `shots / shotsOnTarget / passes / passAccuracy / tackles / interceptions` — 신규 필드 (시즌 통계용)
- `xG (expected goals)` — 신규 필드 (V1.x 검토)

#### 3.5.5 텍스트 이벤트 (사용자 피드백 2.9)
- **유저 구단 매치 한정** 텍스트 이벤트 생성.
- `Match.events: List<MatchEvent>` (placeholder 기존) 본격 사용.
- `MatchEvent.cs`:
  ```csharp
  public class MatchEvent {
      public int minute;
      public MatchEventType type;       // Goal / Shot / Card / Injury / Sub / KeyPass / Save / FullTime
      public int actorPlayerId;         // 주체 선수
      public int targetPlayerId;        // 어시스트 / 파울 대상 등 (0 = 없음)
      public string textKey;            // String Table key (§3.15)
      public Dictionary<string, string> textArgs;  // {"player": "이강인", "assist": "손흥민"}
  }
  ```
- 비활성 구단 (BackgroundSimulator) — `match.events` 비움 (생성 X). 메모리 절약 + 비용 ↓.
- UI: `MatchTextController` — 텍스트 이벤트를 분 순서대로 표시 + 가속 (×1 / ×2 / ×4 / 스킵).

#### 3.5.6 부상 / 카드 시스템
- `InjuryTypeSO` (V0.1 정의됨, 미사용) 본격 활용.
- 부상 종류 (FM 표준):
  - Sprained Ankle (1-2주) / Muscle Strain (2-4주) / Hamstring (4-6주) / Knee Ligament (3-6개월) / 등 ~15종.
- 부상 발생 시 `InjuryInfo` 채우기 + `state.fatigue` 0 (회복 중) + `PlayerInjuredEvent` 발행.
- 카드 누적 → 출장 정지:
  - 옐로 5장 시 1경기 정지 (EPL 룰).
  - 옐로 10장 시 2경기, 15장 시 3경기.
  - 레드 = 즉시 1-3경기 정지 (사유별).
- `Player.state.suspendedMatches: int` 신규 필드.
- 스타팅11 선정 시 `injury` / `suspendedMatches > 0` 둘 다 제외.

#### 3.5.7 평점 시스템 (Rating)
- 매 분 이벤트 발생 시 주체 선수 평점 가산점:
  - 골 +1.0 / 어시스트 +0.5 / 키패스 +0.1 / 인터셉트 +0.1 / 옐로 -0.3 / 레드 -1.5 / 자책 -1.0
- 기본 6.5 시작, 매 매치 종료 시 누적 → Round1 (소수 1자리).
- 골키퍼: 세이브당 +0.2 / 무실점 +0.5 / 실점당 -0.3.
- 팀 승리 시 전 선수 +0.2, 패배 -0.2.
- 사기 시스템과 연동 (§3.4.2).

#### 3.5.8 백그라운드 시뮬 경량화
- `BackgroundSimulator.SimulateDay` — 비활성 매치는 **경량 경로** (`SimulateLite`) 분리.
- `SimulateLite`: 분 단위 step 없음. V0.1 와 유사 단순 Poisson + 라인 가중 득점자만.
- `match.events` 비움. `playerStats` 는 goals + minutes 만.
- 옵션: `MatchPostProcessor.Process(..., publishEvent: false)` — UI 갱신 비용 ↓.

#### 3.5.9 컵 연장전 / 승부차기 (V1.0 도입 — `algorithms.md` #2 V1.0+ 노트)
- `match.type == FACup / CarabaoCup` 분기.
- 동점 시 연장전 (`extraTimeLambda` ~ `avgGoalsPerMatch × 0.3`).
- 그래도 동점 → 승부차기 (5+ 라운드, `penaltyKick` 이벤트 = `composure` × `finishing` × GK `reflexes`).

> **컵 활성화 자체**는 §3.12 + §5 검토. V1.0 도입 여부 미결정.

#### 3.5.10 외부 영향 (form / morale / fatigue / weather)
- 매치 strength 계산 시 곱셈 보정:
  - `effectiveCA = CA × (1 + (form - 50) / 200) × (1 + (morale - 50) / 200) × max(0.5, 1 - fatigue / 200)`
- 폼 50, 사기 50, 피로 0 = 변동 없음.
- 폼 100 + 사기 100 + 피로 0 = CA × 1.5 (이론치).
- 외부화: 곱셈 계수들 `GameBalanceSO.formCoefficient` 등.

#### 3.6.2 Player Role + Duty (Q10 확정 — 포지션별 3-4 Role)
- 각 포지션 마다 Role 3-4개 선택 가능 (V1.0 = ~40 Role 카탈로그):
  - GK: Goalkeeper / Sweeper Keeper
  - CB: Centre Back / Ball Playing Defender / Stopper
  - LB/RB: Full Back / Wing Back / Inverted Full Back
  - DM: Defensive Midfielder / Anchor / Deep Lying Playmaker
  - CM: Central Midfielder / Box-to-Box / Mezzala
  - AM: Attacking Midfielder / Trequartista
  - LM/RM: Wide Midfielder / Inside Forward
  - LW/RW: Winger / Inside Forward / Inverted Winger
  - ST/CF: Advanced Forward / Target Forward / Poacher / Complete Forward
- **Duty**: Attack / Support / Defend (FM 표준).
- 각 Role × Duty 조합이 매치 시뮬 시 해당 선수의 **이벤트 가중치 변경**:
  - 예: Poacher = `shootingWeight × 1.5`, `passWeight × 0.7`, `defensiveWeight × 0.3`
  - 예: Wing Back (Attack) = `crossingWeight × 1.5`, `tackleWeight × 0.7`
- 데이터: `PlayerRoleSO` (id / name / 호환 포지션 / 디폴트 duty / 매치 이벤트 가중치 modifier).
- **Team Instructions (Tempo / Passing / Pressing 등) 은 V1.x** — V1.0 매치 엔진에서 분기 X.
- `Tactic.cs` 신규 도메인:
  ```csharp
  public class Tactic {
      public int formationId;
      public List<TacticSlot> slots;       // 11개 — 포지션 + Role + Duty
      public Mentality mentality;          // 7단계 enum
      public TeamInstructions instructions;
      public List<int> setPieceTakers;     // 페널티/자유킥/코너 키커
  }
  public class TacticSlot {
      public Position position;
      public int playerRoleSOId;
      public Duty duty;                    // Attack / Support / Defend
      public int assignedPlayerId;         // 0 = 자동
  }
  ```
- `Club.tactic: Tactic` 신규 필드 (구단별 1개, V1.x 다중 전술).

#### 3.7.4 검색 결과 가시성 (Q4 확정 — 이분법 + 모든 선수 조회 가능)
- **결정:** 명단 진입 여부로 **이분법**. 단 명단 밖 선수도 **조회 자체는 가능** — 정확 수치만 가림.
- 검색 결과 표시 정책:
  - **명단 ∈ (Scouted)**: 정확 CA/PA + 정확 stats 수치 + 모든 트레잇 + Hidden Attributes 노출
  - **명단 ∉ (Not Scouted)**: 이름·구단·포지션·나이·국적은 노출. **CA/Stats 는 정성적 라벨**:
    - "매우 높음 (Very High)" / "높음 (High)" / "중간 (Average)" / "낮음 (Low)" / "매우 낮음 (Very Low)" 5단계
    - Hidden Attributes 는 **완전 비공개** (라벨도 X)
    - 트레잇 = 일부 노출 (`displayName` 만, 효과 X)
- `TransferSearchFilter` 의 `requireScouted: bool` 폐기 — 모든 선수 검색 가능 (단 정확도 다름).
- 디버그 모드 (`isDebugMode`) — 명단 무관 정확 수치 모두 노출 (개발/QA 용).
- **UI 시각화**: 명단 ∈ 선수 = 배경 강조 / 명단 ∉ = 회색조 + 자물쇠 아이콘 / "스카우트 추가" 버튼 (V1.x).
- **효과**: 시설 등급 ↑ = 사실상 모든 선수 정확 수치 가능. 시설 Lv1 = 자기 리그 일부만 정확, 나머지 정성적.

#### 3.7.5 AI 구단 영입 시스템 (CpuTransferAi — 사용자 피드백 2.7, Q3 확정 — **필요 기반 트리거**)
- **결정:** 횟수 / 빈도 X. **각 구단의 영입 필요 상황 발생 시점에 오퍼**. FM 처럼 자연스러운 시장 움직임.
- 각 AI 구단도 자체 스카우트 명단 보유 (§3.7.1-2).
- **필요 트리거 (매주 `EventScheduler` 또는 `DailyProcessor` 호출)**:
  1. **약점 포지션 식별** — 각 4라인 평균 CA 가 명성 대비 ratio `expectedMeanCA × 0.95` 미만 → 그 라인 영입 필요. **(최우선 트리거)**
  2. **부상자 발생** — 핵심 선수 (CA 상위 ≥ 70%) 가 4주+ 부상 시 → 같은 포지션 영입 시도.
  3. **계약 잔여 6개월** — 핵심 선수가 FA 임박 시 → 대체 영입 시도 (`amount = current player 시장가 × 1.0`).
  4. **약속 미이행 위험** — 보드 약속 (시즌 시작 시 영입 약속) 임박 + 미이행 → 약속한 포지션 영입.
  5. **명성 대비 자금 여유** — 자금 > `clubReputation × balance.aiSavingsThreshold` 면 명성 합의 강화 영입 (slow accumulation 회피).
- 트리거 발생 시 **자기 명단 ∩ 그 포지션 ∩ 자금 안** 선수 추첨 → `SubmitOffer(amount = marketValue × random(1.20 ~ 1.40))`.
- 트리거 우선순위: 약점 라인 > 부상자 > FA 대체 > 약속 > 자금 여유. 같은 클럽이 같은 주 여러 트리거면 1개만 (자금 분산 회피).
- **시드**: `state.randomSeed ^ club.id ^ currentDate.Ticks ^ trigger.type` (결정성 유지).
- **이적시장 활성화 기간 외에도 트리거** — 미리 협상 (`design-decisions.md` #37 V0.1 정신 일관).
- 외부화:
  - `aiWeaknessRatioThreshold = 0.95`
  - `aiCoreInjuryWeeksThreshold = 4`
  - `aiSavingsThreshold = 1000` (만원 단위)
  - `aiOfferAmountRandomMin = 1.20` / `aiOfferAmountRandomMax = 1.40`
- 명세: `algorithms.md` #7 신규 작성 (CpuTransferAi — Stage F).

- 단 같은 시설은 한 번에 1단계만 (Lv2 → 3, 3 → 4 동시 불가).
- UI: Facility 화면에 현재 진행 중 업그레이드 목록 + 새 발주.

#### 3.10.4 비용 인상 (사용자 피드백 — "너무 쌈")
- V0.1: Lv 1 → 2 가 ~100k.
- V1.0: 명성 / 자금 기반 재밸런싱. 빅클럽 (자금 9M) 도 한 시즌 모아 Lv3 → Lv4 가 부담스럽게.
- 외부화 곡선: `FacilityLevelSO[type].upgradeCost / upgradeDuration`.
- 비용 = `baseCost × pow(level, 2.5)` + 노이즈 (대략 Lv1→2 = 50k, Lv9→10 = 5M).

#### 3.10.5 시설 효과 본격 도입 (V0.1 미구현 → V1.0 효과 적용)

**D.4 직접 도입 (`design-decisions.md` #53 / `algorithms.md` V1.0-10 + V1.0-11):**
- **Training Lv N** → 매월 1일 1군 선수 stat 성장 확률 가산. `growthChance = baseChance (0.05) × ageFactor × absoluteFactor × (1 + N × 0.10) × paFactor`. Lv1 ×1.1, Lv10 ×2.0.
- **Medical Lv N** → 부상 회복 일수 `÷ (1 + N × 0.05 + gymLevel × 0.02)` + 부상 발생률 `× max(0.5, 1 - N × 0.05)` (floor 0.5).
- **Gym Lv N** → 피지컬 stat 8개 (Acceleration / Agility / Balance / Jumping Reach / Natural Fitness / Pace / Stamina / Strength) 한정 성장 보정 `× (1 + N × 0.05)` + 부상 회복 일부 `× (1 + N × 0.02)`.

**후속 Stage 의존 (D.4 책임 X):**
- **Stadium Lv N** → 시즌 입장료 수입 = `baseStadiumIncome × N × clubReputation × homeMatches`. (Stage M.6 — SeasonEndProcessor 재정 결산)
- **Scout Lv N** → 스카우트 명단 크기 (Lv1=~50, Lv10=~3000) + 정확도. (Stage E.2 — `ScoutingSystem`)
- **YouthCoach Lv N** → 유스 평균 PA + 고급 트레잇 부여 확률. (Stage L.3)
- **YouthRecruitment Lv N** → 유스 풀 크기 + 인스펙션 빈도. (Stage L.3)
- **YouthFacility Lv N** → 유스 성장률 + 1군 콜업 적응. (Stage L.3)

**나이 곡선 (Training 성장 시스템):**
- 16-22세: peak growth (+1.5 ~ +0.9)
- 23-26세: prime (+1.0 ~ +0.5)
- 27-30세: 정체 (0)
- 31세+: decline (-0.2 ~ -1.0)

#### 3.10.6 시설 등급 표시 (UI)
- V0.1: "Lv 3" 숫자만.
- V1.0: "Lv 3 / 10" + 이번 등급 효과 + 다음 등급 효과 + 비용 + 완료까지 일수.

              state.saveVersion++;
          }
          return state;

  }

### 6.3 시드 (`design-decisions.md` #17) 영향

- 매치 시드 (`match.id ^ randomSeed`) — 이벤트 시퀀스로 변경되지만 동일 시드 = 동일 시퀀스 유지.
- 유스 시드 (현재 6 요소) — Mentoring 도입 시 변경 없음 (Mentoring 효과는 매월 deterministic 계산).
- AI 영입 시드 — `state.randomSeed ^ club.id ^ currentDate.Ticks` (CpuTransferAi 일관).
- Save Migration 시드 — V0.1 → V1.0 변환에서 HiddenAttributes 생성 시 `state.randomSeed ^ player.id` derived.
